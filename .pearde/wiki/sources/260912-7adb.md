# the pegged-syspolicyd dyld hang is keyed by inode, so a hardlink runs and a copy does not

Refines [[260912-7a41]] and [[260912-ebde]]. While `/usr/libexec/syspolicyd` is
pegged, the rule is not "every newly *linked* Mach-O hangs". It is sharper:

**dyld's code-signing verdict is cached per file identity (inode), not per
path.** A binary whose inode already has a verdict runs normally, from any
path. A binary whose inode has no verdict blocks in `_dyld_start` forever,
because the pegged daemon never answers the request.

The three-way test that shows it, on one known-good old binary
(`~/.cargo/bin/kache`, built Sep 6, verdict long cached):

    exec original path+inode      -> exit 0    (runs)
    exec hardlink, new path       -> exit 0    (runs — inode carried the verdict)
    exec APFS clone, new inode    -> exit 142  (hangs in dyld)

`cp -c` / `cp` / `clonefile` all produce a new inode and therefore all hang.
`ln` does not.

**The trap this sets.** A binary that was *created* during the peg never got a
verdict, so it hangs even from its own original inode — it looks like a
counter-example to the rule and is not. Choose the subject for this test from
before the peg began, or you will "refute" the rule with a binary that simply
never ran. This cost one wrong conclusion before it was caught.

**What it buys a stalled Rust build.** Pointing `CARGO_TARGET_DIR` at a warm
target directory from before the peg lets cargo reuse build-script *outputs*
without re-executing them, which carries the build well past the ~10-crate wall
(to the heavy leaf crates: tokio, mlua, rustix, tempfile). But an APFS clone of
that directory defeats itself — every cached `.dylib` and `build-script-build`
gets a fresh inode and hangs on load. The fix is to hardlink the executables
and proc-macro dylibs rather than copy them, so they keep their verdicts:

    for p in debug/deps/*.dylib debug/build/*/build-script-build; do
      rm -f "$CLONE/$p" && ln "$ORIG/$p" "$CLONE/$p"
    done

Hardlinking only the executables and dylibs (not the whole tree) is the safe
form: cargo replaces those by create-and-rename, never in-place, so unlinking
one leaves the original untouched. Hardlinking fingerprint/JSON files would not
be safe, because cargo does rewrite those in place and would corrupt the source
tree's cache.
