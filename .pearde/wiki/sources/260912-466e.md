# A cartridge document can declare a subtree namespace before anything loads a subtree, and the gap shows as a need binding outside its own parent

The answered fork on the cartridge manifest — `provide` keys private to a
cartridge's own subtree, visible outward only where a parent re-exports them —
splits cleanly into a part the document can carry alone and a part it cannot.

What the document carries alone, and now does: `export` is validated against
what the cartridge's own subtree actually offers, one level at a time.
`Cartridge::offered` reads the direct child directories holding a
`cartridge.json`, collects each child's `provide` plus each child's own
`export`, and stops — a grandchild's key reaches the top only when every level
between passes it on. Two cartridges may therefore declare the same key without
colliding, and a re-export naming a key nothing inside offers is refused at
read time, before the Lua entry is evaluated.

What it cannot carry: nothing loads a nested cartridge. The profile's
`init.lua` is still the only way a cartridge enters the graph. Run
`probe/end-to-end.sh` and the symptom is exact — `outer` declares
`needs: ["inner.store"]`, its own child `outer/inner` provides that key, and
`zirkle list` prints `inner.store <- other`, binding it to an unrelated
top-level cartridge. The child was never loaded, so the lookup had nothing
nearer to find.

So the subtree is a property of the document today and a property of the graph
only once a ledger scans a cartridge root and a resolver walks outward from the
asking cartridge rather than searching one flat list. Neither is a defect in
the document; both are the next two contracts.

Where not to look for the fix, read rather than tried: the inject-to-provider
search in `Host::manifest` and `deps()` in `src/main.rs` both iterate the
profile's entry list, which is flat by construction. There is no subtree in
that list to walk until something enumerates one, so scoping the lookup there
would have nothing to scope against.
