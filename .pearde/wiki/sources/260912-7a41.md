# A pegged syspolicyd hangs every freshly linked Mach-O in _dyld_start

On macOS 25.2 (Darwin 25.2.0, Apple silicon), when `/usr/libexec/syspolicyd`
gets stuck at ~100% CPU, every newly linked Mach-O binary hangs forever in
`_dyld_start` before reaching `main`. Nothing crashes and nothing errors: the
process simply sits at 0% CPU indefinitely, because dyld blocks waiting on the
code-signing/provenance verdict that syspolicyd is no longer answering.

What this costs a build. `rustc` itself still runs — it was linked long ago and
its verdict is cached — so compiling a single source file appears to work. The
stall is anything the build must *execute*: `build.rs` scripts and proc-macro
dylibs. On this repo `cargo check --offline` compiled roughly ten crates and
then every process sat at 0% CPU until it was killed at 480s. `cargo build`,
`cargo check` and `cargo test` therefore do not fail, they hang, and each
attempt leaves a stuck `cargo` process behind.

The cheap probe, which distinguishes a broken crate from a broken machine:

    d=$(mktemp -d)
    printf 'fn main(){println!("hi");}\n' > "$d/h.rs"
    rustc -o "$d/h" "$d/h.rs" || exit 1
    perl -e 'alarm 20; exec($ARGV[0])' "$d/h"
    echo "exit=$?"   # 0 healthy, 142 hung in dyld

The remedy is restarting the daemon, not the machine. `sudo killall syspolicyd`
— launchd respawns it immediately — with `sudo killall amfid` as its companion,
since the two cooperate on the same verdict. A full reboot works but is not
required, which matters when the person at the keyboard has a session they do
not want to lose. Both need `sudo`, so an agent cannot clear this itself; it
has to be handed to the user as a command to run.

Verified on /Users/feb/dev/cartridge, 2026-09-12: syspolicyd pid 498 at 98.6%
CPU across two days, probe exit 142, three unrelated workarounds tried and
none helped.
