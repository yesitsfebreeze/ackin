# A ledger scanned off a cartridge root closes the nesting gap, and the whole cost lands in one boolean and one same-scope tie

[[260912-466e]] left two contracts open: nothing loaded a nested cartridge, and
the lookup searched a flat profile list. A ledger built from the filesystem
closes the first completely and is cheaper than it looks.

**What the build did, all of it green.** `src/ledger.rs` (~230 lines) scans a
root: a directory is a cartridge exactly when it holds `cartridge.json`; the
root's direct children are top-level entries and a cartridge's direct children
are its nested entries, recursively, keyed by the `/`-joined path from the root.
`Ledger::resolve(from, key)` walks outward — the asker's own children first,
then its parent's children, out to the root — and binds to the first entry whose
`provide` or `export` holds the key. `Host::entries` in `src/loader.rs` now
derives one entry per installed cartridge before `init.lua` is read at all, and
the profile is laid over as an override. `zirkle ledger` prints the tree with
each need bound. `cargo test` 68 passed, `warnings = "deny"` clean.

The exact symptom 466e recorded is gone: `outer` needing `inner.store`, with its
own child providing it and an unrelated top-level cartridge providing the same
key, now prints `store.get <- outer/inner` instead of binding to the stranger.

**Three things that cost a test run each, and are not obvious.**

1. **Match an override by the file it resolves to, not by the string written.**
A profile entry may name the cartridge folder (`path="p"`) or the document
inside it (`path="p/cartridge.json"`). `Entry::file` already makes those one
cartridge; comparing the raw `path` strings instead makes them two entries, both
load, and `folders::watcher_reloads_a_folder_when_its_manifest_changes` fails on
a duplicated event rather than on anything about watching.

2. **An override replaces the derived entry; it does not merge into it.** Two
profile entries may name one folder — `{id="bad",path="bad"}` beside
`{id="off",path="bad",disabled=true}` in
`manifest::an_unreadable_document_asks_for_nothing_knowable_not_for_nothing`,
and two `p.lua` instances in `reload::two_entries_of_one_file_each_get_their_own_switch`.
Any positional "find the match and overwrite it" loop eats the second one. The
shape that works is three lines: collect the files the overrides name, `retain`
the derived entries whose file is not among them, then extend with the
overrides. Instancing survives untouched.

3. **Deriving nested cartridges as top-level entries breaks the settled
namespacing rule, and the compiler cannot see it.** With every ledger entry
made an entry of the profile, `outer/inner`'s `provide` lands in the flat
runtime registry and is visible to everything —
`manifest::a_parent_passes_an_inner_key_outward_by_naming_it` goes from 1 listed
cartridge to 2, and `probe_nesting_is_not_discovered` flips. Deriving only
`parent().is_none()` entries keeps both green. Loading a nested cartridge is the
resolver's contract, not the ledger's; the ledger registers it and stops.

**The two open forks, both reproducible.**

*Does an installed cartridge run?* Exactly one line decides it — the `disabled`
default in `Host::derived` — and exactly one assertion separates the two
answers. `src/tests/bridge.rs` rewrites `init.lua` without a folder and asserts
the cartridge stops; under auto-registration it does not stop, because the list
is no longer the record. `disabled: true` is 68/68; `disabled: false` is 67/68
with that one assertion down. The PRD's words ("neither involves editing a
list") point at `false`; the-resolver's words ("uninstalling is the absence of a
launch") point at `true`. The board has to say which.

*Two entries of one scope offering one key.* The settled rule says two
cartridges may provide the same key without colliding, and that is true across
subtrees. Inside one scope it is not: with `other` providing `store.get` and
`far` re-exporting it from `far/deep`, a root-level ask prints
`store.get <- far` — first in path order, silently, with no diagnostic. Path
order at least makes it deterministic across runs; it does not make it chosen.

**A non-cartridge folder does not extend a subtree.** `vendor/hidden` with a
document but no document at `vendor` is in no subtree and reachable by nobody.
That falls straight out of "a subtree is a chain of cartridges" and wanted no
decision, but it means grouping installed cartridges into plain folders under
the root silently hides them. Worth knowing before someone tidies a directory.
