# a spawn-harness startup benchmark on this host carries a 1.0ms floor, so subtract it or the number is not the binary's

Measuring a CLI's startup by timing `subprocess.run` or a shell loop measures the host's `fork`/`exec` as well, and on this machine that is not small.

**Paired measurement is the fix, and it is cheap.** Time N runs of the subject and N runs of `/usr/bin/true` on the same loop, in the same process, and report the difference. `.pearde/prds/the-host-binary/probe/help-latency.sh` does this for 200 runs each.

Numbers for `zirkle --help`, a debug-profile Rust binary that parses argv with clap and exits:

| harness | `/usr/bin/true` | subject | net |
|---|---|---|---|
| `sh` loop, 200 runs | 1.001 ms | 3.070 ms | **2.069 ms** |
| python `subprocess.run`, 40 runs | 1.098 ms | 3.187 ms | **2.089 ms** |

Two unrelated harnesses agree on the floor (~1.0 ms) and on the net (~2.07 ms) to within 1%. So the floor is the host, not the harness.

**The negative result, which is the expensive half.** The-host-binary PRD carries a measured claim of `0.9ms` for this same `--help` on this same machine, against Bun 8.9ms / Deno 12.1ms / Python 15.6ms / Node 24.0ms. That 0.9 ms does **not** reproduce here by any method tried: wall is 3.07 ms and net-of-spawn is 2.07 ms, and 0.9 ms is below even the `/usr/bin/true` floor, which no binary on this host can beat. The method behind it was not recorded. Do not treat it as a regression baseline — it is un-reproducible, not un-met, and the comparison row against Bun/Deno/Node is only sound if all five were measured the same way.

Corollary for any acceptance box worded "under N ms": say which number it means. Wall and net differ by 50% at this scale, and a box that does not say can be argued either way after the fact.

Also worth knowing when reading fast build times on this host: `rustc-wrapper = "kache"` is set in `~/.cargo/config.toml`, so a full recompile of a crate can report 0.5s. That is a cache hit, not a fast compiler.
