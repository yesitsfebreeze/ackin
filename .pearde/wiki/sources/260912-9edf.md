# a warm cargo target dir does not restore a compile signal under a pegged syspolicyd

The negative result that follows from [[260912-7adb]]. Worth recording because
the idea is the obvious one to try next and it costs about an hour to rule out.

**The idea.** `cargo build` under a pegged `syspolicyd` dies because build
scripts and proc-macro dylibs are freshly created Mach-Os with no verdict. So
point `CARGO_TARGET_DIR` at a target directory built *before* the peg: cargo
reuses the cached artifacts, executes nothing new, and the build completes.

**How far it gets.** Genuinely further. Against a warm tree the build ran past
the previously recorded ~10-crate wall and reached the heavy leaf crates —
`tokio`, `mlua`, `rustix`, `tempfile`. Build-script *outputs* are reused from
the cache without re-executing the scripts, so that whole class of stall
disappears.

**Where it still dies, and it is not where you would guess.** `sample(1)` on
the stalled `rustc` shows it is *not* hung at process start — it reaches
`main`, loads `librustc_driver`, and enters `run_compiler`. The block is:

    run_compiler -> dlopen_from -> Loader::getLoader -> makeJustInTimeLoaderDisk
      -> Loader::mapSegments -> SyscallDelegate::fcntl -> __fcntl

That `fcntl` is the code-signature check on a **proc-macro dylib being
dlopen'd**. Same daemon, same peg, different moment — so `ps` showing a live
`rustc` at 0% CPU is this, not a jobserver deadlock.

**Why it cannot be salvaged on this machine.** Per [[260912-7adb]] the verdict
is cached per inode, so hardlinking the cached dylibs into the working tree
should carry their verdicts across. It does — the inodes match — and it still
hangs, because **every proc-macro dylib in the warm tree was itself created
during the peg** and so never had a verdict to cache:

    find target/debug/deps -name '*.dylib' -newermt '<peg start>'  -> 31
    find target/debug/deps -name '*.dylib' ! -newermt '<peg start>' ->  0

Check that before spending the hour: if `! -newermt <peg start>` returns zero
dylibs, there is no warm cache to borrow and this route is closed before you
start.

**Also ruled out this pass:** removing the `RUSTC_WRAPPER` (`kache`, set in
`~/.cargo/config.toml` as `rustc-wrapper`) changes nothing — the wrapper is an
old binary with a cached verdict and is not implicated; the build stalls at the
identical point with it disabled.

**Conclusion.** Under a pegged `syspolicyd` there is no route to a Rust compile
signal without `sudo killall syspolicyd` (plus `sudo killall amfid`). An agent
without root should stop looking, leave the compile boxes open, and say so.
