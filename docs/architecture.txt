# System architecture

Read alongside development.txt, creating-cartridges.txt, and memos.txt.

REPOSITORIES AND OWNERSHIP

~/dev/cartridge is a Git parent containing .gitmodules, submodule directories,
and a forwarding justfile. The source repository is cartridge.ctg. The other
submodules are loadable cartridges.
Each cartridge keeps its implementation and cartridge.json in its own repository.
cartridge.ctg/builtin/<name> links to ../../<name>.ctg, so a source change is
visible to the runtime without copying it into a second source tree.
repositories.json is the development catalog, not a second capability manifest.

The source repository owns src/, scripts/, profiles in .cartridge/, memos,
the shared cartridge workspace in workspace/Cargo.toml, and ignored target/,
dist/, and validation/ directories. The runtime is a standalone Cargo workspace;
13 Rust cartridge packages share workspace/Cargo.toml; memory has its own Cargo
workspace. scripts/workspace.py shares target output across these workspaces.

THE HOST

src/runtime.rs and src/fiber.rs manage active components and their lifecycles.
src/lua.rs supplies the Lua composition API. src/loader.rs reads cartridge.json,
resolves its Lua entry, reads profile entries, and observes source changes.
src/ledger.rs records installed declarations and bindings; src/resolver.rs
resolves service dependencies. A profile selects which cartridges participate.

A typical invocation follows this path:
  launcher -> selected profile -> manifest and Lua entry -> applied component
  -> registered service -> JSON request -> JSON result -> component disposal.
A daemon keeps the composition active; run performs one foreground invocation.
call contacts an already-running profile through its local socket.

DECLARATIONS AND COMPOSITION

cartridge.json names the cartridge and a relative Lua entry. provide names
services it offers; needs names required services; export passes inner service
keys outward. When provide/needs are nonempty, the document replaces the Lua
entry's corresponding declarations. Missing declarations can fall back to Lua.
Keep SDK hello declarations and the document consistent rather than relying on
fallback to hide mismatches.

Nested keys are private to their subtree. Each parent must export an inner key
for it to travel outward another level. Two separate subtrees may use the same
key privately. The resolver rejects invalid or ambiguous visible bindings.

ISOLATION

A cartridge brings its own surface and registers into the host; the host is
the only thing that knows the list. Across a boundary there are two paths: a
declared need (needs, or a key the profile injects) called directly, and an
event listened to. A key never declared is refused at the point of use, at any
depth (undeclared access). A cartridge carries no sibling's protocol for an
optional feature and no rule about a sibling; the tool's descriptor says which
of its ops only read (reads), and the composition's config.lua says what the
policy asks about. Installing or removing a cartridge therefore changes nothing
outside it. `just isolation` reports every source line that breaks this.

THE MANUAL

cartridge help is built from what is installed and enabled: one line per
cartridge from its cartridge.json description, and for `cartridge help <id>`
the declarations off that document followed by the page the cartridge ships at
.cartridge/help.md, with links relative to its directory. `cartridge help
<word>` searches every page; --json is the manual as one document; `cartridge
help host` is the runtime's own page beside the profile. A cartridge without a
page is reported and the overview exits non-zero.

SETTINGS

settings in cartridge.json declares the configuration keys a cartridge
contributes: type, default, optional bounds, and one line of documentation per
dotted key. The host fills every declared key, checks kind and bounds, and hands
the cartridge a complete configuration, so a cartridge carries no fallbacks and
re-checks no bound the declaration already states. The document is the only
place the numbers live: no Default impl restates them and no configuration
field takes #[serde(default)]. A cartridge embeds its own cartridge.json and
reads the declared table back through settings::declared for an unhosted run.
The host's own keys are declared in settings.json beside llms.txt and live
under host; src/settings.rs names them to give them types.

Layers, each laid over the last field by field: the declaration, then manifest
config, then ~/.cartridge/config.lua for the machine, then the project's
.cartridge/config.lua, then the profile entry config in init.lua. Tables merge;
scalars and lists replace; an explicit null returns a key to its default. Both
config.lua files are keyed by entry id; do not commit live credentials to
either. cartridge settings prints every key with its value and the file that
settled it, and exits non-zero on a configured key nothing declares. See
settings.txt.

Free functions that cannot read a configuration carry a limits module instead:
one struct deserialized from the settled table, installed once by the cartridge
before it serves, its defaults read back off the same document. harness,
sessions, gitfs, pty, router, docs and memo each carry one, declared as their
limits.* keys; memo carries a second for its source adapters under sources.*.

.cartridge/init.lua returns entries such as:
  return {{id="sessions", path="sessions"}, {id="policy", path="policy"}}
path resolves below the selected cartridge directory, normally builtin/.
config.lua returns per-entry settings. Entry-level config, disabled, inject,
and isolate are supported; inspect loader::Entry before changing their shape.
The default, mcp, proxy, and tools profiles compose different application uses.

PROCESS AND EVENT WIRE

A Lua cartridge registers services directly with ctx:provide. A Rust cartridge
uses init.lua containing return cartridge.process("<binary>") and implements
cartridge::sdk::Cartridge. Its hello mode reports declared dependencies/services.
The SDK speaks JSON lines over stdin/stdout; application diagnostics belong on
stderr. The host applies configuration, routes calls and replies, forwards events,
and coordinates disposal. stdout logging would corrupt the protocol.

src/cartridge.rs handles the wire, src/sdk.rs its cartridge-facing API, and
src/process.rs child execution. src/socket.rs exposes the persistent host to
clients; src/stream.rs manages channel subscriptions and event envelopes.
src/trace.rs and src/context.rs carry invocation context. SDK hosts can themselves
spawn child cartridges, preserving explicit outward service declarations.

Four dispatches carry an event to the listeners registered for its name, and
the difference between them is what they do with the answers: ctx:emit ignores
them, ctx:bail takes the first non-null one and stops, ctx:parallel keeps only
the errors, and ctx:gather keeps every answer, each attributed to the fiber
that gave it. A listener that fails fails its own fiber under emit and gather,
so one cartridge that cannot answer never costs the caller the rest.

THE FABRIC ANNOUNCE

src/fabric.rs serves two questions about the composition. The snapshot
({"snapshot":true} on the wire, Host::snapshot in the SDK) is the raw
read-only view of what the host loaded. The graph ({"graph": scope},
Host::graph) fires the fabric.announce event and gathers what the
composition answers: every active cartridge contributes {"nodes","edges"} in
the shapes src/graph.rs reads, core states the entries and their
provide/inject edges itself, and core stamps each announced node with the
answering entry's id rather than trusting the answer's own claim. Which
cartridges are composed is therefore what the graph is. `scope` is the asking
side's context, passed through to contributors — a session cwd, say, since core
has no session of its own. The SDK answers the announce for every cartridge
without being asked to: the tools it provides, as each describes itself now.
Host::announce adds what only that cartridge knows, such as a record's memos.
Nothing is cached: asking rebuilds.

REPLACEMENT AND RESOURCES

The loader watches relevant sources and configuration. src/reload.rs coordinates
replacement generations. SDK on_reload hooks participate where configured;
on_dispose releases resources. Register owned tasks/listeners through lifecycle
APIs and exercise replacement with real state. A change being detected is not
proof that arbitrary background work or external state migrates correctly.
Do not terminate unrelated daemons to test replacement; use isolated profiles.

PERMISSIONS AND POLICY

The manifest grant is a capability request with read, write, net, and exec lists.
An absent grant requests nothing. Reading the document never evaluates Lua or
executes its commands. Commands are documentation and confer no capabilities.
The strict parser rejects unknown fields, including misspelled permission keys.

The policy cartridge separately answers allow, ask, or deny for tool requests.
Do not treat a policy answer as proof of operating-system isolation. Sandbox
backend and launch integration require checking the current implementation
and tests before claiming a particular confinement boundary. Keep profile policy changes explicit and narrowly scoped.

INSTALLED CARTRIDGES

agent: model/tool conversation orchestration.
fs: filesystem tools and file operations.
gitfs: Git-backed file and workspace operations.
harness: prompt/context composition, including system memos and memory.
mcp: exposes the composed tool surface over MCP stdio.
memo: typed Markdown record, discovery, validated writes, and composition context.
memory: durable knowledge storage and retrieval, with a standalone CLI, and
  the tool.memory adapter over it.
policy: Lua tool decisions and configured per-tool rules.
proxy: authenticated HTTP entry point for model-compatible requests.
pty: terminal processes, shell operations, and terminal environment services.
router: configured model/provider selection and routing.
sessions: conversation/session persistence.
tools: building bundles and managing development worktrees.
ui: terminal interface and its host bridge.

For exact service keys and dependencies, read the relevant cartridge.json through
just describe <name>. For API payloads, inspect its source and service metadata.
Do not infer a service name or tool schema from the repository name alone.
