# Writing good cartridges

ONE CAPABILITY

A cartridge owns one capability and everything that belongs to it: its
events, its settings, its state, its tests and its help page. Another
cartridge reaches it only through the events it declares.

DEFINE, LISTEN, NEED

Define an event where its meaning lives: a tool's owner defines the tool event
with its input schema and listens to it; a session store defines
`session.start` and emits it. Listen to what you answer. Need what you cannot
run without: the base starts you only once a listener is active.

Pick the send by what you do with the answers:

  emit      nothing; fire and forget
  bail      the first answer; the listeners are alternatives, in profile order
  gather    every listener's outcome, attributed: answered, declined, failed,
            timed_out or unavailable

Give an event that does slow work a `timeout_ms` that fits it; a sender stops
waiting for a listener at that deadline.

An optional feature with several possible providers is an event prefix in
`needs` (`"tool.*"`): every event with that prefix another enabled cartridge
listens to; `cartridge.needs()` lists what arrived.

SCHEMAS

Give every event a schema. It is the contract listeners rely on and the check
that stops a wrong payload at the sender with a field named, instead of a
confusing failure somewhere down the line.

ISOLATION

A cartridge sends only events it declares or needs, to listeners it does not
choose, over a token minted for that edge. It carries no sibling's protocol
and names no sibling. Its native code runs inside its own sandboxed node with
the grant it declared.

STREAMS

Publish what others may want to watch as it happens on a channel, and keep the
payload self-contained: a subscriber may join late and read the replay. Name
channels after what they carry.

STATE AND RESTARTS

A cartridge can be restarted at any time: its socket and tokens stay the same,
sends in flight fail, and senders reconnect. Keep durable state on disk under a
granted path, make startup cheap, and make operations safe to retry. Clean up
in on_dispose.

ERRORS

A listener's error travels to the sender as its message. A listener that fails
publishes the failure on its own `error` channel; the sender is not the party
that broke. Diagnostics go to stderr, one JSON object per line where possible;
the base records them.
