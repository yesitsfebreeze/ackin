# Events: how cartridges talk

Everything between cartridges is an event. A cartridge declares the events it
defines, the events it listens to and the events it needs a listener for, in
its cartridge.json. Its init.lua registers listeners with the injected
`cartridge` global and sends events through it. The base validates every
declaration before a cartridge starts; every payload is checked when it is
sent and again when it arrives.

DECLARATION

  "events": { "session.start": { "description": "…", "schema": { …JSON Schema… }, "timeout_ms": 5000, "frame": "data" } }
  "listen": ["tool.read", "session.start"]
  "needs":  ["memory.query"]

  events   what this cartridge defines: the name, one line of purpose, a
           JSON Schema for the payload, and how long a sender waits for each
           listener (`timeout_ms`; absent, the base's `event_timeout_ms`).
           `frame` says what the payload may become in a model's context:
           `message`, `data` or `none`. The set is closed, so no declaration
           claims system or developer authority; any other value refuses the
           manifest, naming the event. Absent, the event states no frame.
           One owner per event.
  listen   what this cartridge listens to. Its listener's return value is the
           answer; nil is no answer.
  needs    events this cartridge sends that must have a listener before it starts.

A cartridge may send exactly the events it defines and the events it needs.

A tool is an event its owner listens to: fs declares `tool.read` with its input
schema and listens to it; anyone sends `tool.read` and takes the answer.
The base owns and listens to one event itself, `tool.asp` (asp.txt); its owner
reads `host`.

CHECKS

Before a cartridge starts, every name in `listen` and `needs` must be an event some
enabled cartridge declares; otherwise it fails with "listens to `x`, which no
cartridge declares" and never runs. An event declared by two cartridges fails
the later one. A cartridge waits until every `needs` event has an active
listener; `cartridge status` names what it waits for.

Before an event is sent, its payload is checked against the schema; a payload
the schema rejects is refused at the sender with the failing field, and no
listener sees it. An event nobody declares, or one the sender neither defines
nor needs, is refused the same way. The listener's node checks both again on
arrival and refuses what fails, whatever the sender did.

OUTCOMES

Every send ends, for each listener, in one outcome:

  answered     the listener returned a value
  declined     it returned nil
  failed       it raised an error, or refused the event
  timed_out    no answer within the event's timeout_ms
  unavailable  it could not be reached

THE LUA GLOBAL

The base injects `cartridge` into every init.lua:

  cartridge.listen(name, fn)      listen; name must be in `listen`. fn(data) returns the answer
  cartridge.emit(name, data)      send to every listener, do not wait; outcomes other
                                  than answered and declined go to this cartridge's `error` channel
  cartridge.bail(name, data)      send in order: the first answer wins, a decline asks
                                  the next, any other outcome raises
  cartridge.gather(name, data)    send to all, wait: one {outcome=, from=, data=|error=} per
                                  listener, in profile order
  cartridge.notify(name, data)    emit, and publish on the channel `name`
  cartridge.publish(channel, data)
  cartridge.subscribe(cartridge, channel, fn)
                                  watch another cartridge's channel; fn(envelope)
  cartridge.needs()               the events this cartridge needs, all covered
  cartridge.events()              every event: name -> {owner, description, schema}
  cartridge.host(method, params)  status, snapshot, cartridges, asp (asp.txt), and
                                  declarations: this cartridge's own events as its
                                  manifest declares them, frame included
  cartridge.on_dispose(fn)        runs when the cartridge stops
  cartridge.load(name)            a native Lua module shipped by this cartridge
  cartridge.spawn(cmd, opts)      a helper program: :request(v), :send(v), :on_line(fn), :kill()
  cartridge.pipe([fn])            a FIFO path a module's threads write lines to
  cartridge.name, cartridge.config, cartridge.root, cartridge.trace()
  cartridge.array_metatable       the table that marks a Lua table as a JSON array

init.lua registers at top level. A function it returns runs on dispose.

Every listener, subscriber, line handler, disposer and init.lua itself runs as
a coroutine. `bail`, `gather`, `subscribe`, `host` and a helper's `request` and
`send` yield while they wait, so one node serves many events at once, and an
event that comes back to its sender is answered while the sender's handler
waits. Where Lua cannot yield, from a native module's Rust code or inside a
sort comparator, the same call blocks the node until it returns; keep long
waits in init.lua.

NATIVE MODULES

A cartridge written in Rust is a Lua module: a cdylib exporting
`luaopen_<name>` (mlua with the `module` feature, linked with `-undefined
dynamic_lookup` on macOS). It imports nothing from the base: inside the Lua
state it reads the `cartridge` global to send events. A module's own mlua does
not share the base's array marker, so a table it means as a JSON array (an empty
one above all) gets `cartridge.array_metatable` set as its metatable. A module's
own threads must not call into Lua: the module's mlua and the base's lock the
state separately. A thread that has something to say writes a protocol line
(below) to a `cartridge.pipe`; the node serves it itself.

PROTOCOL LINES

A helper program's stdout and a pipe carry lines of JSON. The node serves these
shapes in Rust, without touching Lua, so they work while a Lua handler is busy
waiting, for example on `:request`:

  {"emit"|"notify": name, "data": …}                     sent to listeners
  {"publish": channel, "data": …}                        published on this cartridge's channel
  {"ask": id, "bail"|"gather": name, "args": …}          answered as {"ask": id, "result"|"error": …}
  {"ask": id, "host": method, "params": …}               the same, for a host query

On a helper's stdout the answer to an ask is written to its stdin; on a pipe
it reaches the pipe's `fn`. Asks are answered out of line, so several may be
in flight. A line with an `id` answers the `:request` with that id; any other
line reaches the `:on_line` handler (or the pipe's `fn`) in order, one at a
time. init.lua loads it with
`cartridge.load("<name>")` from the cartridge folder (or target/{release,debug}
while developing) and wires its functions to events. Lua cannot yield across a
native call, so a module's own `bail`, `gather`, `subscribe` or `host` blocks
its node until it returns; long waits belong in Lua or on the module's threads.

STREAMS

A channel belongs to the cartridge that publishes it. The publisher keeps a
bounded replay buffer and serves `subscribe` with `since`; a subscription
survives the publisher restarting. A subscriber that falls a full queue behind
is disconnected and resubscribes from the last envelope it took. The base serves `lifecycle` on the host
socket: state transitions and failures of every cartridge. A `lifecycle` subscriber that falls behind is
disconnected too; it has no `seq` to resume from, so it reads `status` again.

NODES

Each cartridge runs as a node: the base binary re-run on that init.lua, in its
own sandboxed process, serving JSON-RPC 2.0 on its own local socket. The wire
is internal: the base hands every node a directory, and updates it whenever the
composition changes. The directory describes every event, but carries sockets
and tokens only for the listeners of events the node may send. Tokens are
minted per edge: one for each sender and listener pair, and one for the node
and the base. A node also receives, for each token it accepts, the sender and
the events it may send there, so a token grants nothing at any other node and
nothing beyond its events. A node answers `event`, `subscribe`, `unsubscribe`,
and for the base `apply`, `directory` and `dispose`. A reload is a stop and a
start on the same socket. Both ends of a local connection check the other's
uid: a client refuses an endpoint it does not own or that another user serves,
and a listener drops a connection from another user without answering and
keeps serving.

Queues are bounded. A connection runs at most 64 requests at once and queues
1024 frames each way; a sender that outruns its listener waits, and a peer that
stops reading is disconnected.

CLI

  cartridge run <event> '<json>'     start the profile, send, print the first answer, stop
  cartridge call <event> '<json>'    the same on the running host; a string answer prints as plain text
  cartridge send <event> '<json>'    every listener's outcome on the running host
  cartridge follow lifecycle | <cartridge>.<channel>
  cartridge status | reload [<id>] | stop
