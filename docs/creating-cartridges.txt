# Creating a cartridge

Read architecture.txt for how the base runs cartridges and transport.txt for
the event model. writing-good-cartridges.txt covers what makes one good.

A CARTRIDGE

Two files in a folder under the cartridge root, here `hello/`.

cartridge.json:
{
  "name": "hello",
  "entry": "init.lua",
  "description": "Greets whoever asks.",
  "events": {
    "hello.greet": {
      "description": "A greeting for a name.",
      "schema": {"type": "object", "required": ["name"], "properties": {"name": {"type": "string"}}}
    }
  },
  "listen": ["hello.greet"]
}

init.lua:
cartridge.listen("hello.greet", function(args)
  return "hello " .. args.name
end)

Enable it in .cartridge/init.lua:
  return { {id = "hello", path = "hello"} }

and send it an event:
  cartridge run hello.greet '{"name":"you"}'

Everything the entry can do is on the `cartridge` global; transport.txt lists
it. To use another cartridge's event, declare it in `needs` and send it:

  "needs": ["hello.greet"]
  cartridge.listen("welcome", function(args) return cartridge.bail("hello.greet", args) end)

WHAT THE ENTRY RUNS IN

Lua 5.4 with the safe standard library: no io, no package, no require, no
dofile or loadfile, and os trimmed to clock, date, difftime, getenv and time.
The state belongs to this cartridge alone and is capped (host.lua_memory_bytes).
Lua that runs host.lua_instruction_budget instructions without handing control
back — waiting on bail, gather, host or a spawned program hands it back — is
refused. Raise either in config.lua if a cartridge does real work in Lua; 0
turns the limit off. Catching your own refusal and carrying on ends the node.

A RUST CARTRIDGE

The Rust code is a Lua module the entry loads. Cargo.toml:

  [lib]
  crate-type = ["cdylib"]
  [dependencies]
  mlua = { version = "0.12", features = ["lua54", "module"] }

build.rs (macOS resolves the Lua API against the base at load time):

  fn main() {
      if cfg!(target_os = "macos") {
          println!("cargo:rustc-cdylib-link-arg=-undefined");
          println!("cargo:rustc-cdylib-link-arg=dynamic_lookup");
      }
  }

src/lib.rs:

  use mlua::prelude::*;

  fn greet(_: &Lua, args: LuaTable) -> LuaResult<String> {
      Ok(format!("hello {}", args.get::<String>("name")?))
  }

  // Reaching the base from Rust: the global is already in the Lua state.
  fn remember(lua: &Lua, note: String) -> LuaResult<LuaValue> {
      let cartridge: LuaTable = lua.globals().get("cartridge")?;
      cartridge.call_function("bail", ("memory.remember", note))
  }

  #[mlua::lua_module]
  fn hello(lua: &Lua) -> LuaResult<LuaTable> {
      let module = lua.create_table()?;
      module.set("greet", lua.create_function(greet)?)?;
      module.set("remember", lua.create_function(remember)?)?;
      Ok(module)
  }

init.lua:

  local hello = cartridge.load("hello")
  cartridge.listen("hello.greet", hello.greet)

The module's crate must not share a Cargo workspace with the base. Ship the
built `libhello.dylib` (or `.so`) in the cartridge folder; while developing,
`target/release` and `target/debug` beside init.lua are searched too.

A module function blocks the whole node while it runs, so a wait on the base
(a bail to another cartridge) belongs in init.lua, where it yields: the module
builds the request, the listener bails, the module shapes the answer. A
cartridge that does long work keeps its own threads or runtime inside the
module, or waits in Lua, where a send yields. Those threads never call into
Lua: they write protocol lines to a FIFO from `cartridge.pipe()` in init.lua,
and the node serves them.

A HELPER PROGRAM

A cartridge may start a program in any language and speak to it over lines of
JSON; the program knows nothing of the base.

  local app = cartridge.spawn({"bun", cartridge.root .. "/src/main.ts"})
  cartridge.listen("live.status", function(args) return app:request({op = "status"}) end)
  app:on_line(function(line) if line.event then cartridge.emit(line.event, line.data) end end)

`request` writes one line with an `id` and returns the line the program writes
back with that `id`. A program that needs the base while answering writes an
ask line, `{"ask": "a1", "bail": "memory", "args": …}`, and reads the answer on
its stdin; it emits and publishes with `{"emit": …}` and `{"publish": …}` lines
(transport.txt, PROTOCOL LINES). Every other line goes to `on_line`. Its stderr
is recorded by the base. Its executable must be in the cartridge's `grant.exec`.

MANIFEST FIELDS

name and entry are required; entry is a relative .lua path inside the folder.

  description     one line of purpose
  events          name -> {description?, schema?}; events this cartridge defines
  listen          events listened to
  needs           events that must have a listener before this cartridge starts;
                  `tool.*` names every event with that prefix another enabled
                  cartridge listens to, and nothing when there is none
  grant           {read, write, net, exec}; absent grants nothing
  settings        dotted key -> {type, default, optional?, min?, max?, doc?}; see settings.txt
  config          author defaults laid over the declared ones
  contracts       events in `listen` that prove the cartridge; `cartridge verify` sends them
  setup           an event in `listen` that `cartridge setup` sends after installing it
  doctor          an event in `listen` that `cartridge doctor` sends
  commands        label -> {argv, cwd, description?}; documentation, never run by the base
  binary          executable basename when it differs from the folder
  ui              a JavaScript or TypeScript client module inside the folder
  source          where the source lives

Names are nonempty exact strings, except a trailing `*` in `needs`. Unknown
fields are refused. A schema that is not a JSON Schema is refused.

CONTRACTS

`cartridge verify` starts the profile and sends every event in `contracts` to
its cartridge with null; an error or `false` fails.
`cartridge verify <id>` starts only that cartridge and what its needs resolve
to in the ledger.

SETUP AND DOCTOR

`cartridge setup` sends the `setup` event {answers, interactive} and reads back
an object: `ask` is a list of {key, prompt, default?} put to the person, whose
answers join `answers` on the next send; `config` is the table written under
the entry's id in .cartridge/config.lua; `done` (or an empty `ask`) ends the
exchange; `note` is printed. Without a terminal every question takes its
default, and one without a default stops the exchange.

`cartridge doctor` sends the `doctor` event {} to every enabled cartridge that
declares one and expects {ok, problems}; any `ok` false, error or other answer
fails the command.

THE HELP PAGE

Ship .cartridge/help.md: a title, two to four sentences on what the cartridge
owns and who reaches it, a "## Use" list of its events and how to send them,
and a "## Read next" list of its own documents. `cartridge help <id>` prints
it, then the declarations from cartridge.json and every other document the
cartridge ships. Do not restate events, needs or settings on the page.

LOCAL STATE

A cartridge keeps its state under the project's .cartridge/<its folder> and
names it in `grant.write` (`${config.dir}`, `$PROJECT/...`). In its own
repository, .cartridge/.gitignore is a whitelist: `/*` ignores the folder and
`!/name` brings back durable entries (help.md, docs/, tests/).
